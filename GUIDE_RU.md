# DAA3: простое объяснение и подготовка к защите

## 1. Что вообще делает этот проект

Здесь слово **граф** означает набор вершин и рёбер. Например, районы города -
это вершины, а дороги между ними - рёбра. У каждого ребра есть целый вес:
стоимость дороги, длина маршрута или время выполнения зависимости.

В проекте решаются четыре практические задачи:

1. Как соединить все районы с минимальной общей стоимостью - Kruskal и Prim.
2. Какие вершины ориентированной сети взаимно достижимы - Kosaraju.
3. В каком порядке выполнять зависимые задания - Kahn.
4. Как найти кратчайшие пути в сети без циклов - DAG shortest paths.

**Граф** и **график** - разные вещи. Граф является структурой данных, а три
PNG-графика в `results/plots/` показывают результаты эксперимента.

## 2. Как запустить в IntelliJ IDEA

Открой именно папку `C:\Users\mukie\IdeaProjects\DAA3` как Maven-проект.
Project SDK должен быть Java 17 (`ms-17`).

В Terminal IntelliJ:

```powershell
.\mvnw.cmd clean test
```

Быстрая проверка benchmark только на `n = 1000`:

```powershell
.\mvnw.cmd -q compile exec:java '-Dexec.args=--quick --output=results-quick'
```

Полный обязательный benchmark:

```powershell
.\mvnw.cmd -q compile exec:java '-Dexec.args=--full'
```

Чтобы показать преподавателю историю разработки:

```powershell
git log --graph --oneline --decorate --all
```

В истории должны быть отдельные ветки `feature/dsu`, `feature/mst`,
`feature/scc`, `feature/paths`, `feature/metrics` и итоговая ветка `main`.

После полного запуска должны появиться:

- `results/results.csv` - заголовок и 50 строк;
- `results/plots/operations-vs-n.png`;
- `results/plots/scans-per-edge.png`;
- `results/plots/kruskal-edge-share.png`.

Почему генератор корректен: для undirected-графа сначала строится случайное
остовное дерево по перестановке `perm`, поэтому граф гарантированно связен. Для
DAG вершинам задаётся случайный ранг, и каждое ребро направляется только от
меньшего ранга к большему, поэтому вернуться назад и образовать цикл невозможно.
Каждый из трёх графов получает собственный новый `Random(42)`.

## 3. Как хранится граф

`Graph` использует **список смежности**. Для каждой вершины хранится список
исходящих рёбер. Поэтому просмотр соседей занимает время, пропорциональное их
количеству, а весь обход - `O(V + E)`.

Для ориентированного ребра `u -> v` запись добавляется только в список `u`.
Для неориентированного `u - v` в списках смежности находятся две дуги: `u -> v`
и `v -> u`. Но в общем списке `edges()` логическое ребро хранится один раз,
чтобы Kruskal не сортировал его дважды.

Разрешены:

- петля `u -> u`;
- несколько одинаковых рёбер;
- изолированная вершина без рёбер;
- несвязный граф.

Формат файла:

```text
n m directed
u v weight
u v weight
...
```

Вместо `directed` можно написать `undirected`. Вершины имеют номера `0..n-1`.

## 4. DSU: как быстро понимать, соединены ли вершины

DSU хранит непересекающиеся множества. В начале каждая вершина является
отдельным множеством.

- `find(x)` идёт по родителям и находит корень множества.
- **Path compression** после поиска напрямую связывает пройденные вершины с
  корнем. Следующие поиски становятся короче.
- `union(x, y)` объединяет множества, только если их корни различны.
- **Union by size** подвешивает меньшее дерево под большее. Дерево не становится
  высоким.

Вместе эти две эвристики дают амортизированное `O(alpha(n))`. Функция
`alpha(n)` растёт так медленно, что для любых практических размеров это почти
константа.

Простой ответ на защите: «DSU нужен Kruskal. Если корни концов ребра уже
одинаковые, между вершинами есть путь и новое ребро создаст цикл».

## 5. Kruskal

Алгоритм смотрит на граф как на общий список рёбер:

1. Сортирует рёбра по весу.
2. Берёт самое дешёвое ещё не рассмотренное ребро.
3. Через DSU проверяет, находятся ли концы в разных компонентах.
4. Если да - добавляет ребро и объединяет компоненты.
5. Если граф связный, останавливается после получения одной компоненты.

Почему результат минимален: самое лёгкое ребро, пересекающее любой разрез,
безопасно добавить в MST. Это **cut property**. Kruskal каждый раз выбирает
такое безопасное ребро между двумя текущими компонентами.

Сложность: сортировка `O(E log E)`, операции DSU почти константные. Итого
`O(E log E)`, дополнительная память `O(V + E)` из-за копии списка и DSU.

На несвязном графе получается не одно дерево, а минимальный остовный лес.

## 6. Prim

Prim растит дерево из уже посещённых вершин:

1. Начинает с вершины `0`.
2. В `PriorityQueue` хранит дешёвые рёбра на границе дерева.
3. Берёт самый дешёвый вариант.
4. Если вершина уже добавлена, старый вариант пропускается.
5. Иначе вершина и выбранное ребро входят в дерево, затем рассматриваются её
   соседи.
6. Если очередь опустела, но остались непосещённые вершины, начинается новая
   компонента. Поэтому алгоритм возвращает лес, а не падает.

Prim тоже использует cut property: выбирает самое лёгкое ребро из текущего
дерева наружу. Эта реализация добавляет новую запись при улучшении и позднее
пропускает устаревшую. В очереди может быть `O(E)` записей, поэтому строгая
оценка - `O(E log E)`, память `O(V + E)`. С indexed heap и настоящим
decrease-key была бы оценка `O(E log V)`.

Важно на защите: у этой lazy-реализации нет универсального теоретического
преимущества на dense-графах перед Kruskal - у обеих оценка `O(E log E)`. Prim
естественно работает с adjacency list и оказался быстрее в нашем измерении.
Классическое `O(V^2)` преимущество на очень плотном графе относится к другой
реализации Prim с массивом или матрицей.

Kruskal и Prim могут выбрать разные рёбра при одинаковых весах. Проверять нужно
одинаковую **общую стоимость**, количество компонент и равенство
`edges = V - components`.

## 7. Kosaraju и SCC

SCC - максимальная группа вершин, где из каждой вершины можно добраться до
каждой другой.

Kosaraju делает два DFS:

1. Первый DFS записывает вершину только после обработки всех её соседей. Так
   получается порядок завершения.
2. Все рёбра разворачиваются.
3. Второй DFS идёт в обратном порядке завершения. Каждое новое дерево второго
   прохода является одной SCC.

Почему второй DFS не смешивает компоненты: если сжать каждую SCC в одну вершину,
получится condensation DAG. Ещё не обработанная компонента с максимальным
временем завершения первого DFS является источником этого DAG. После reverse
она становится компонентой без выходов в другие необработанные SCC, поэтому
второй DFS остаётся внутри неё.

Оба обхода сделаны **без рекурсии**. Используются собственные массивы-стеки,
поэтому путь из 100 000 вершин не вызывает `StackOverflowError`. Первый стек
хранит вершину и индекс следующего соседа - без этого нельзя правильно получить
finish order.

Сложность: `O(V + E)`, память `O(V + E)` вместе с reversed graph. Счётчик
`edgeScans` относится именно к двум DFS: каждый из них просматривает все `m`
рёбер, поэтому `edgeScans = 2m`. Построение reversed graph отдельно проходит
ещё по `m` рёбрам, но в этот счётчик не входит; общая сложность всё равно
остаётся линейной `O(V + E)`.

## 8. Kahn и топологический порядок

`indegree[v]` - количество рёбер, входящих в вершину `v`.

1. В очередь помещаются все вершины с `indegree = 0`.
2. Вершина извлекается и добавляется в порядок.
3. Для каждого исходящего ребра уменьшается indegree соседа.
4. Когда indegree стал нулём, сосед готов и попадает в очередь.

Если извлечено меньше `V` вершин, оставшаяся часть содержит цикл. Тогда проект
возвращает признак цикла и **не выдаёт частичный список как правильный ответ**.

Проверка порядка: для каждого ребра `u -> v` должно быть `pos[u] < pos[v]`.
Сложность `O(V + E)`, память `O(V)`, а на DAG `edgeScans = m`.

## 9. Кратчайшие пути в DAG

Здесь используется виртуальный super-source. Его не нужно физически добавлять:
расстояние `0` получают все вершины с нулевой входящей степенью.

В конечном DAG каждая цепочка предшественников обязана закончиться вершиной с
`indegree = 0`, иначе возник бы цикл. Значит, виртуальный источник действительно
делает достижимой каждую вершину. `parent[v]` всегда является более ранней
вершиной топологического порядка, поэтому цепочка родителей тоже не может
зациклиться.

1. Получаем топологический порядок Kahn.
2. Если есть цикл, останавливаемся.
3. Идём по вершинам в топологическом порядке.
4. Для каждого ребра пробуем relaxation:
   `dist[v] = min(dist[v], dist[u] + weight)`.
5. При улучшении записываем `parent[v] = u`, чтобы восстановить путь.

Отрицательные веса безопасны: в DAG нет цикла, поэтому нельзя бесконечно снова
проходить отрицательный цикл. Когда приходит очередь вершины, все возможные
предшественники уже обработаны.

Доказательство индукцией: у источников верное расстояние `0`. Предположим, что
для всех предыдущих вершин расстояния верны. Каждый путь в текущую вершину
заканчивается ребром из уже обработанного предшественника. Мы проверили все такие
рёбра, значит выбрали минимум. После обработки всех вершин верны все расстояния.

Сложность `O(V + E)`, память `O(V)`, `edgeScans = m`.

## 10. Что означают счётчики

Счётчики увеличиваются **внутри алгоритмов**, а не вычисляются формулой после:

- `dsu_ops = findCalls + successfulUnions`;
- `edge_scans` - реально просмотренные рёбра или дуги;
- `comparisons` - сравнения весов/стоимостей;
- `max_depth` - максимальный размер собственного стека Kosaraju.

Каждый из пяти измеряемых запусков получает новые счётчики. В CSV записывается
один воспроизводимый набор, а время является медианой пяти запусков.

У `DagShortestPath` время охватывает весь вызов: сначала Kahn строит
топологический порядок, потом выполняется relaxation. Но счётчик этой строки
по условию относится только к relaxation, поэтому `edgeScans = m`, а не `2m`.

Контрольные равенства:

- Kosaraju: `edgeScans = 2m`;
- Kahn на DAG: `edgeScans = m`; при цикле очередь может остановиться раньше;
- DAG shortest paths: `edgeScans = m`;
- Prim на неориентированном списке: ровно `edgeScans = 2m`;
- Kruskal: `edgeScans <= m`, потому что на связном графе он может закончить
  раньше.

Для связного benchmark-графа у Kruskal ровно `n - 1` успешных объединений, а
каждая проверка ребра вызывает два `find`. Поэтому можно дополнительно проверить
точное равенство `dsuOps = 2 * edgeScans + (n - 1)`.

## 11. Как читать три PNG-графика

1. **Operations vs n**. Обе оси логарифмические. Прямая с наклоном около `1`
   означает линейный рост. У Kruskal линия немного круче из-за сортировки
   `E log E`.
2. **Scans per edge**. Если `edgeScans / m` остаётся почти постоянным, число
   операций действительно пропорционально `E`.
3. **Kruskal edge share**. Показывает, какую долю отсортированных рёбер Kruskal
   успел проверить до построения дерева. На плотном графе нужные дешёвые рёбра
   часто встречаются раньше, поэтому доля может быть меньше.

Slope не вписан вручную: `BenchmarkStatistics` берёт `ln(n)` и `ln(operations)`
для пяти точек и находит наклон обычной линейной регрессией
`cov(x, y) / var(x)`. Полный benchmark печатает эти значения в консоль.

Время зависит от ноутбука, JVM и фоновых программ. Поэтому главные доказательства
сложности - счётчики и их отношения, а `time_ms` является дополнительным
наблюдением.

## 12. Как выбрать алгоритм

| Ситуация | Что выбрать | Почему |
|---|---|---|
| Есть список рёбер, нужен MST | Kruskal | Простая сортировка и DSU |
| Есть adjacency list, растим от вершины | Prim | Удобная граница через priority queue; на наших dense-входах был быстрее, но это не универсальная гарантия |
| Нужны все SCC | Kosaraju | Два линейных итеративных обхода |
| Нужно расписание зависимостей | Kahn | Даёт порядок и сразу обнаруживает цикл |
| Нужны shortest paths, граф точно DAG | DAG shortest paths | Один линейный проход, можно отрицательные веса |
| Возможны циклы и отрицательные веса | Не DAG-алгоритм | Нужен, например, Bellman-Ford |

## 13. Короткие ответы на вопросы агая

**Почему не matrix?** Для разреженных графов матрица требует `O(V^2)` памяти,
а список смежности - `O(V + E)`.

**Почему нужны и union by size, и path compression?** Первая эвристика не даёт
строить высокие деревья, вторая уплощает уже пройденные пути. Вместе они дают
почти константную амортизированную стоимость.

**Почему петля не войдёт в MST?** Оба конца уже в одной вершине/компоненте, значит
DSU отклонит её. Prim тоже не добавляет уже посещённую вершину.

**Почему MST может отличаться, а вес совпадать?** При равных весах может быть
несколько разных минимальных деревьев.

**Почему рекурсивный DFS нельзя?** Глубина 100 000 может переполнить стек JVM.
Собственный стек хранится в heap и контролируется программой.

**Как Kahn видит цикл?** В цикле ни у одной оставшейся вершины indegree не станет
нулём. Очередь опустеет раньше, чем будут обработаны все вершины.

**Почему отрицательные веса разрешены в DAG?** Нет циклов, значит нет
отрицательного цикла и каждая вершина обрабатывается после всех предшественников.

**Почему benchmark воспроизводим?** Каждый новый граф использует новый
`Random(42)`, порядок вызовов генератора фиксирован, а результаты сверяются с
таблицей из задания.
